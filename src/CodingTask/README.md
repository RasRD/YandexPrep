# Задача 4. Проверка лимитов платежей

**60 минут на реализацию и xUnit-тесты, затем 30 минут обсуждения.** API, модели и тест-кейсы спроектируй самостоятельно.

Реализуй асинхронный сервис проверки нового платежа. Вход: `userId` (`long`), сумма (`decimal`), `CancellationToken`. Две асинхронные зависимости предоставляют:

- Лимиты пользователя: максимальную сумму одного платежа и общую сумму за день.
- Историю успешных платежей пользователя: суммы и время проведения, за разные дни, в произвольном порядке.

Нужны только контракты зависимостей и тестовые замены.

## Правила

1. `userId > 0`, сумма `> 0`. Некорректные аргументы отклоняются до вызова зависимостей; контракт ошибки выбери сам.
2. Платёж разрешён, если его сумма не превышает разовый лимит, а сумма вместе с историей за текущий день — дневной. **Равенство разрешено.**
3. День — `[00:00 UTC, 00:00 UTC следующего дня)`. Текущее время считывается один раз в начале корректного запроса; выбранный день не меняется при ожидании. В тестах время должно задаваться без реального ожидания и изменения системных часов.
4. Три результата: разрешено, превышен разовый лимит, превышен дневной лимит. При превышении обоих приоритет у разового.
5. Ошибки зависимостей завершают проверку ошибкой, отмена — отменой; ни то ни другое не превращается в бизнес-результат. Можно пробрасывать исходные исключения.
6. Уже отменённый токен исключает вызов зависимостей; иначе передавай им отмену вызывающего кода. При сочетании отмены с некорректными аргументами допустим любой из двух исходов. При гонке отмены с готовым результатом также допустим любой исход. Зависимости поддерживают отмену; принудительная остановка не нужна.
7. Проверка ничего не записывает и не резервирует: решение относится только к полученным данным.

## Допущения

- Одна валюта, суммы имеют не более двух знаков после запятой; округление не нужно. Лимиты существуют для любого корректного `userId`, неотрицательны и неизменны во время проверки. Ответы зависимостей корректны, не `null`.
- В истории только успешные платежи нужного пользователя с положительными суммами и временем UTC. Нет дубликатов, возвратов, отменённых, проверяемого нового и будущих относительно зафиксированного момента платежей.
- История помещается в память, переполнений нет. Вызовы сервиса не пересекаются; зависимости могут завершаться сразу или после ожидания. Параллельность необязательна. Ненужные данные можно не запрашивать; количество обращений не оценивается.
- HTTP, БД, DI-контейнер, кеш, повторы, собственные таймауты и пагинация не нужны. Библиотека моков необязательна. Конкурентная проверка с регистрацией платежа — отдельное последующее усложнение.

## Пример

Разовый лимит **500**, дневной **1000**. В истории: **650 сегодня**, **900 вчера**. Независимые проверки: **350 → разрешено**, **350,01 → дневной лимит**, **501 → разовый лимит**.
