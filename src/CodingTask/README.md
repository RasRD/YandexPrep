## Условие базовой версии

Реализуй сервис оформления заказа интернет-магазина. Он получает клиента и корзину, вычисляет итоговую сумму с персональной скидкой и списывает купленные товары со склада. Вся работа выполняется в памяти одного процесса.

Исходные данные:

- Каталог задаётся при создании сервиса. У товара есть уникальный положительный `productId` типа `long`, цена типа `decimal` и начальный остаток типа `int`.
- Каталог корректен: цены неотрицательные и содержат не более двух знаков после запятой, остатки неотрицательные. Цены не меняются; пополнения склада нет. Текущие остатки меняет только сервис оформления заказа.
- Клиент содержит имя и персональную скидку в процентах типа `decimal`. Имя гарантированно непустое. Допустимая скидка — от 0 до 100 включительно.
- Корзина содержит строки с `productId` и количеством типа `int`. Один товар может встретиться в нескольких строках.

Правила:

1. Корзина должна быть непустой. Количество в каждой исходной строке должно быть строго положительным. `null` вместо клиента, корзины или её строки считается некорректным аргументом.
2. Для повторяющихся товаров количества складываются. Доступность товара проверяется по суммарному количеству.
3. Цены берутся из каталога. Скидка применяется ко всей сумме заказа. Итог округляется один раз, после применения скидки, до двух знаков после запятой; при точной середине — от нуля (`MidpointRounding.AwayFromZero`).
4. Успешное оформление уменьшает остатки всех купленных товаров и возвращает имя клиента и итоговую сумму.
5. При некорректном аргументе, скидке вне диапазона, неизвестном товаре или недостатке хотя бы одного товара оформление завершается ошибкой. **При любой из этих ошибок все остатки сохраняются без изменений.**
6. Способ представления ошибок выбери сам и зафиксируй в контракте. Вызывающий код должен отличать некорректные данные, неизвестный товар и недостаточный остаток. При нескольких ошибках разрешено сообщить любую одну; приоритет не задан.
7. Предусмотри способ узнать текущий остаток известного товара, чтобы поведение можно было проверить через публичный API.

Пример:

| Товар | Цена | Начальный остаток |
|---|---:|---:|
| A | 100,00 | 5 |
| B | 50,00 | 2 |

Корзина: A × 1, B × 1, A × 2. Скидка клиента: 10%.

Ожидается сумма **315,00**, остатки **A = 2**, **B = 1**.

Границы базовой версии:

- Вызовы последовательные; потокобезопасность пока не требуется.
- Входные объекты вызывающая сторона во время выполнения метода не меняет. После инициализации каталог извне не изменяется.
- Данные ограничены так, что суммы количеств и денежные вычисления помещаются в выбранные типы; отдельная обработка переполнения не требуется.
- Каждый вызов означает новую покупку. Хранение истории заказов, оплата, доставка, возвраты и защита от повторной отправки запроса не входят в условие.
- Достаточно обычного проекта C# и xUnit. БД, HTTP, внешние сервисы и асинхронные операции не нужны для этого контракта.

## Что сделать самостоятельно

Спроектировать модели и публичный API, реализовать сервис и написать xUnit-тесты. Набор тестов выбрать самостоятельно. До реализации кратко описать контракт ошибок и своё понимание правил. Готовые сигнатуры, реализация и список тест-кейсов намеренно не предоставлены.

Ориентир по времени: 5–10 минут на уточнения и контракт, 30–35 минут на реализацию, оставшееся время — на тесты и проверку. Подготовка пустого проекта и проверка запуска тестов выполняются до старта таймера. Код и тесты писать без ИИ; справочник по API допустим.

После попытки прислать код, тесты, фактическое время и отметить обращения к справке или подсказкам. На ревью оцениваем соответствие этому контракту, осмысленность тестов, читаемость и способность объяснить поведение. Новые требования не используются для оценки базовой версии.
